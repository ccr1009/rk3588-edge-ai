## 一、结论：舵机坏了

### 完整证据链（每一项都是实测，不是推测）

| # | 测量项 | 手段 | 结果 |
| :-: | :--- | :--- | :--- |
| 1 | 舵机电源电压（红线↔棕线） | 万用表 DCV 20V | ✅ **4.8~5.2V** |
| 2 | 共地（电源 OUT- ↔ ESP32 GND） | 万用表通断档 | ✅ **响** |
| 3 | PWM 到舵机端（橙线↔GND） | 万用表 DCV 20V | ✅ **≈0.25V** |
| 4 | 固件 PWM 波形（pad 自测） | 固件 `R 14` 回环 | ✅ **pw_avg=1499us per_avg=20000us** |
| 5 | 引脚确认 | 固件 `I` | ✅ **GPIN 14 15** |
| 6 | **舵机动作**（三次慢扫 + 6 次交替 + 中位 6 秒） | 肉眼观察 | ❌ **完全不动、没声音** |

**三根线全都收到了正确的电信号，舵机毫无反应 → 内部驱动电路已损坏。**

### 为什么排除其它可能

| 嫌疑 | 怎么排除的 |
| :--- | :--- |
| 5V 没到 | 测 1 实测 4.8~5.2V |
| 共地断了 | 测 2 实测通断档响 |
| 橙线没接 / 接错针 | 测 3 实测 0.25V，且 `I` 回 `GPIN 14 15` |
| 固件 / PWM 有问题 | 测 4 实测 1499us / 20000us 标准波形 |
| 是 360° 连续旋转舵机 | 若是，会「单向持续旋转」；实际**完全不动** |
| 信号发到 GPIO40 上了 | 曾因脚本误发 `X` 触发引脚扫描，已修正并确认回到 GPIO14 |

### 损坏原因（推测）

反复带电改线，某一次红线碰了 GND 或棕线碰了 5V → 内部驱动 IC / 电机线圈烧毁。
这也解释了「11-03 单舵机能用 → 11-04 起完全没反应」这个时间线。

## 六、本次排查修掉的两个真 bug

### bug 1：DTR/RTS 拉高导致 ESP32 一直复位

`usb_cdc_serial.py` 原来固定发 `SET_CONTROL_LINE_STATE = 0x03`（DTR+RTS 都拉高）。

对 ESP32-S3 来说，`0x03` 等价于「按住自动下载电路」→ 芯片反复复位 →
`app_main` 永远跑不到处理命令那步。但 **USB 描述符是 ROM 提供的，app 没跑照样在**
→ 现象是「`lsusb` 能看到、pyusb 能打开、但一个字都不回」。

逐组试出来：

| DTR/RTS | 结果 |
| :--- | :--- |
| `0x03`（都拉高） | ❌ 0 回应 |
| **`0x00`（都拉低）** | ✅ **`GPIN 14 15`** |

已改成 `0x00`，并加了**自动探活**（打开后发一次 `I`，没回应就依次试 `0x03/0x01/0x02`）。

> 教训：**「能打开」和「能通信」是两件事。** 不能用"打开成功"当作通路正常的判据。

### bug 2：测试脚本误发 `X` 命令导致引脚被改走

`definitive_test.py` 第一版把 `X` 当成「重置状态」放进清场命令里。
但固件里 `X` = `start_scan()`，是**启动引脚扫描**：

```c
case 'X': start_scan();     // 开始遍历 SCAN_PINS[]，每 1.2s 换一个脚
```

而主循环里扫描优先级最高：

```c
else if (g_scanning) update_scan();    // ← 扫描期间 P 命令完全不生效
```

结果：整个测试的 PWM 都发在错误引脚上（读到过 `GPIN 40 15`），舵机当然不动。
**如果没发现这个，会误判成"舵机坏了"——虽然结论恰好对了，但那是运气。**

已修正为只发 `D 0` / `A`，并加了「确认引脚回到 14」的前置检查。

## 九、这个坑对校招项目的价值（面试能讲）

不要把它当成纯粹的挫折。这是一个**完整的故障定位案例**：

**① 分层排查法：先证明软件无罪，再查硬件**

固件里写了 `R` 回环自测 —— 让 ESP32 把输出脚同时当输入，
用边沿中断 + `esp_timer` 微秒时间戳量自己 pad 上的真实电平。
在没有示波器的前提下拿到 `pw_avg=1499us / per_avg=20000us` 的硬数据，
把「舵机不动」切成了「信号有没有出到引脚」这个可验证问题。

**②「症状相同 ≠ 故障相同」**

5V 没到 / 共地断了 / 舵机烧了 —— 三者症状一模一样（没声、没锁、摇臂松）。
靠改线试错收敛不了。正确动作是**停下来引入测量**，而不是增加试错次数。
万用表到位后 10 分钟就确诊了，而这之前盲改了两天。

**③ 中间层会伪装成故障源**

桥接服务只放行 4 条命令，其余本地回 `ERR unknown_cmd`，
让上游完全看不到「命令根本没到设备」。我们因此误判固件没烧进去。
**教训：中间层要么透明转发，要么回包里带上自己的标识。**

**④「能打开」不等于「能通信」**

USB CDC 打开成功 ≠ 通路正常。DTR/RTS 拉高会让 ESP32 持续复位，
而 USB 描述符由 ROM 提供、app 没跑也在，所以看起来一切正常但一个字节都传不过去。
**判据必须是「收到正确回包」，不能是「打开没报错」。**

**⑤ 文档内部自相矛盾是真实的坑**

README 3.1 写「`5Vin` 是输入脚」，3.2 又写「这三针能同时拿到 GND 和 5V」——
同一份文档两句话冲突。我按 3.2 给了错误建议。
**教训：文档冲突时以「有实测证据的那条」为准，并顺手把冲突改掉。**（已修）

**⑥ 方法论总结（最值钱的一条）**

> 排查顺序必须「从最靠近自己的一层往外」：
> 固件活着吗 → 引脚有波形吗 → 波形到 pad 了吗 → pad 外面通电了吗。
>
> 而「测不到」必须配对照实验 —— 没有对照的阴性结果不能用于归因。
