## 二、核心结论：tilt 和 pan 的物理尺度差 1.87 倍

**这是本次最关键的发现，也是 tilt 抖而 pan 稳的根本原因。**

固件定义（`gimbal_main.c`）：

```c
#define PAN_RANGE_DEG   90.0f   // 指令 ±90 → 物理 ±90°（180° 全行程）
#define TILT_RANGE_DEG  45.0f   // 指令 ±45 → 物理 ±90°（180° 全行程）
```

**同样 1 个指令单位，tilt 转的物理角是 pan 的 2 倍。**

再叠加画面尺度：

| | pan | tilt |
|---|---|---|
| 1 指令单位 = | 2° 物理 | **4° 物理** |
| FOV / 分辨率 | 60° / 1280px | 36° / 720px |
| **1 单位 = 画面像素** | 42.7 px | **80.0 px** |
| 共用 max_step=0.6 时单帧位移 | 25.6 px | **48.0 px** |
| 死区（共用 0.025×1280） | 32 px | 32 px |
| **单帧位移 / 死区** | 80% ✓ | **150% ✗** |

**pan 的单帧位移小于死区所以稳；tilt 是死区的 1.5 倍，每步都冲出死区，必然振荡。**

仿真验证（初始偏差 400px，模拟蹲起幅度）：

| max_step | 单帧 px | 延迟7帧（10°步进） | 延迟10帧（30°步进） |
|---|---|---|---|
| 0.60（原来共用） | 48px | 超调 149，**过零 2 次** | 超调 293，**过零 4 次** |
| 0.20（现在） | 16px | 超调 26，过零 1 次 | 超调 73，**过零 2 次** |
| 0.12 | 10px | 超调 6，过零 1 次 | 超调 35，过零 1 次 |

**过零次数 = 用户看到的"摆几下"。** 原来 4 下，现在 2 下。

### 实测验证

```
tilt 轨迹（真实运行，25 帧）：
  T-14.3 → -14.3 → -14.3 → -14.0（连续 10 帧不动）→ -13.5 → -13.1 → ...
```

**一次到位就停住，不再来回摆。**

## 三、四个真 bug（按价值排序）

### Bug 1：tilt 和 pan 共用 max_step（已修）

见上。修法：

```cpp
float max_step_pan  = 0.6f;    // 42.7 px/单位
float max_step_tilt = 0.20f;   // ★ 80.0 px/单位，必须单独设
float deadzone_pan  = 0.025f;
float deadzone_tilt = 0.035f;  // 垂直死区略大，蹲起是低频大幅动作
```

### Bug 2：`invert_tilt` 方向反了（已修）

原代码 `invert_tilt = true`，注释自己承认「未经实测确认（GPIO15 当时没接舵机）」。

**推导**（基于实测标定）：
```
tilt=-14 → 框顶 y1=404   （头在画面下部）
tilt=-20 → 框顶 y1=29    （头到画面顶部）

⇒ tilt 减小 = 头往画面上方移 = 相机低头
⇒ 头在上方(err<0)时要让头下来 = tilt 增大 = d_tilt > 0
⇒ d_tilt = -err * kp，err<0 时 d>0 ✓
⇒ invert_tilt 必须为 false（true 会取反成负 → 正反馈 → 顶死限幅）
```

**症状对比**：改前 tilt 一路冲到 `+6.9`（抬头看天花板），改后稳定在 `-20~-22`。

### Bug 3：`tgt_cy` 用框高计算，被框大小变化带偏（已修）

```cpp
// 改前：bh 一抖 cy 就跳
tgt_cy = (oy1 + (oy2 - oy1) * HEAD_Y_RATIO) / rows;   // HEAD_Y_RATIO=0.18

// 改后：只跟框顶边
tgt_cy = (oy1 + rows * HEAD_TOP_OFFSET) / rows;        // HEAD_TOP_OFFSET=0.10
```

**实测**：框高从 400 变到 700px 时，旧公式 `cy` 跳 **54px**（这是蹲起时的假信号），新公式 **0px**。

代价：tilt 绝对落点略变（近距离多仰约 2.7°，远景少仰 1.8°）。觉得头被顶太高就把 `HEAD_TOP_OFFSET` 调到 0.12。

### Bug 4：`--no-target-filter` 是假开关（已修）

```cpp
bool filter_partial = false;                          // 默认关
else if (... "--no-target-filter") filter_partial = false;   // 只是再设一次 false
```

**全程序没有任何办法打开过滤。** 所以旧二进制跑起来过滤一直是关的。
已补 `--target-filter` 并默认开启。

## 四、控制律：没有 PID，只有 P

```cpp
float d_pan  = err_pan * kp_pan;     // kp_pan  = 0.20
float d_tilt = -err_tilt * kp_tilt;  // kp_tilt = 0.13
// 变步长
d *= slow_gain + (1 - slow_gain) * sqrt(ratio)
// 积分型：out = 当前角度 + d
```

**没有 I，没有 D。** 且是**积分型**（增量累加到当前位置），不是位置式。

`kp` 取值依据：临界增益 `kp_u ≈ 0.37~0.75`，取 45~60% ⇒ `kp_pan=0.20`。
`kp_tilt=0.13` 更小，因为垂直 FOV 更窄且 tilt 有重力负载。

## 五、变步长（解决"快"与"稳"的矛盾）

固定 `max_step` 无法同时满足两个要求：
- 步子必须远小于死区才不振荡
- 但步子小了追 300px 要 19 帧（0.75 秒），"反应太慢"

```cpp
ratio = (|dx| - deadzone) / (0.5 - deadzone)    // 0=刚出死区, 1=画面边缘
scale = slow_gain + (1 - slow_gain) * sqrt(ratio)
```

**★ 分母是 `0.5 - deadzone` 不是 `1.0 - deadzone`** —— 因为 `dx = cx - 0.5`，`cx∈[0,1]`，所以 `|dx|` 最大 **0.5**。
若照抄 Python 版的 `(1.0-dz)`，ratio 最大只到 0.487，满量程步长只有 0.48，"远处够快"失效。

用 `sqrt` 而非线性：`ratio→0` 处斜率无穷大，离开死区时步长抬得快，避免"卡在边界爬行"。

## 六、控制链路延迟拆解（实测）

| 段 | 数值 | 来源 |
|---|---|---|
| 相机曝光+USB | ~14ms | 推算 |
| V4L2 采集阻塞 | 8.5~9.8ms | profile 实测 |
| 预处理 | 3.7~4.1ms | 实测 |
| **NPU 推理** | **15.1~16.8ms** | 实测 |
| DFL 解码 | 1.2ms | 实测 |
| 画框 | 2.0ms | 实测 |
| JPEG 编码 | 7.0ms | 实测 |
| **TCP 回环** | **0.112ms** | `STAT` p50 实测 |
| **固件 50Hz 节拍** | **均值 10ms**（0~20 变化） | 相位扫描实测 |


严格等于 `20ms - 相位`，均值 10ms。

## 七、为什么做不到大疆 Pocket 3 的丝滑

用户的对照实验很准：「Pocket 3 没什么算力，但真的很丝滑」。

| | Pocket 3 | 本项目 |
|---|---|---|
| **IMU 姿态内环** | **400~1000Hz** | ❌ 完全没有 |
| 视觉外环 | 30Hz | 25.6~27 FPS |
| 电机 | BLDC + FOC | 有刷舵机 |
| **电机响应** | **18~23ms** | **230ms** |
| **角速度** | 300~500°/s | **46~85°/s** |
| 速度环 | ✅ 可给速度指令 | ❌ 只能给位置 |

**Pocket 3 的视觉延迟实测也有 380ms，照样丝滑** —— 因为中间有 IMU 内环吸收抖动。我们没有内环，每个环节的抖动都直接暴露。

**这是硬件本质差异，调参解决不了。** 要那个手感需要换 BLDC 云台（¥1000+）。

### 已知但未修的问题

1. **自适应标度在极远档余量不足**：`dz_scale` 和 `step_scale` 反向变化，4m 外单帧步长/死区比达到 0.99，极远 >6m 达 1.19（理论上一步跨过死区）。全域扫 34200 点验证真判据仍未越界，但余量接近 1。
2. **发送阈值 0.05 会吞掉 tilt 小步长**：tilt 系数 `36×0.13=4.68`，偏差 <14px 时步长 <0.05 被静默丢弃，加重黏滞。
3. **SIGTERM 杀不死**：HTTP 线程阻塞在 `accept()`，`pthread_join` 永久阻塞。测试要用 `timeout -s KILL`。
4. **Python 脚本仍是旧公式**：`track_head_v3.py` 等还是 `HEAD_Y_RATIO=0.18`，与 C++ 对拍会差最多 54px。

## 十、这轮踩的坑（方法论）

1. **用"精度"标准要求反馈控制** —— 我一开始拒绝所有贴边的框，导致 85 帧全拒、一帧不动。**反馈只需要单调，不要求精确。** 裁切框的中心仍与真实位置单调相关，只是增益减半，补偿即可。
2. **拿 2FPS 环境验的参数搬到 25FPS** —— 控制律是积分型 `K=kp/T_frame`，帧率变 12.8 倍行为完全不同。
3. **没有先量指标就反复试角度** —— 应该一开始就算"框占画面比例"，超过 50% 直接判定不可追，而不是试 25 个角度。
4. **把测试脚本的 bug 当成固件 bug** —— `S` 命令回两行（`# slew` + `OK`），只读第一行导致"回包滞后一条"的误判。
5. **算错了归一化尺度** —— 死区像素换算把 1280 当成 640，导致整个稳定性推导错了一半。
